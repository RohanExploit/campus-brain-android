# From Fragile Prototype to Production "Company Brain": A Hybrid SQL + Graph + Vector RAG Blueprint for Yashoda Technical Campus on a 4GB GPU

## TL;DR
- **Your #1 blocker (aggregate/count/threshold queries like "students who failed ≥4 subjects") is architecturally unsolvable by vector, graph, or community-summary retrieval — it requires a fourth engine: a text-to-SQL path over structured records loaded into a local analytical database (DuckDB).** Build a router that detects aggregation intent and dispatches to SQL, keeping your existing FACT/LOCAL/GLOBAL RAG paths for semantic questions. This is a Day-1 need.
- **A 4B model can generate reliable SQL against a NARROW, well-understood schema (single result-sheet table) if — and only if — you add schema-linking, few-shot exemplars, execution-based self-correction, and read-only guardrails.** Small models score badly on cross-domain benchmarks (Qwen2.5-Coder-7B ≈ 45–51% zero-shot on BIRD) but reach the 80s–90s on simpler single-domain schemas. Consider a code-specialized model (Qwen2.5-Coder-3B/7B or SQLCoder) for the SQL path specifically.
- **On RTX 2050 4GB, keep the LLM warm-loaded, FAISS + graph in RAM, embeddings/query results cached, and offload only the SQL model swap; realistic latency is sub-second on cache hits, a few seconds on the SQL path, and 30–120s only for long-context generation.** The determinism win from constrained decoding + SQL means most hard queries finally get *correct* answers, which matters more than raw speed.

## Key Findings

1. **The failing query class is a known, named problem with a known solution.** Aggregate/filter/count/GROUP-BY questions over structured rows are handled by a **text-to-SQL path**, not RAG. The dominant 2026 production pattern is the "intelligent hybrid router": a query classifier that dispatches semantic queries to vectors, relationship queries to the graph, and **aggregation/threshold/count queries to SQL**. This is exactly what your LightRAG-inspired FACT/LOCAL/GLOBAL router is missing — a fourth SQL route. As one hybrid-QA analysis puts it, "LLMs excel at semantic processing but lack correctness guarantees for precise operations. SQL provides efficient, verifiable operations."

2. **DuckDB is the right structured store for this workload**, not SQLite. DuckDB is columnar/vectorized and built for OLAP aggregations (GROUP BY, COUNT, thresholds over many rows), runs in-process with a ~20MB footprint, reads CSV/Parquet/Pandas directly, and dramatically outperforms SQLite on aggregate scans — on a 10-million-row GROUP BY + SUM, DuckDB "typically completes in under one second where SQLite takes over 20 seconds." Use SQLite only for lightweight state/queue/idempotency tracking.

3. **Table extraction from messy PDFs must be a tiered pipeline, not one tool.** No single extractor wins on all document types. Digital PDFs with ruled tables → Camelot (lattice) or Docling; borderless/whitespace tables → pdfplumber; scanned docs → OCR first, then extract; genuinely messy/irregular layouts → LLM-based extraction into a fixed schema. Docling (your current tool) is fast (~10s/page) but was measured at only **63% extraction accuracy vs. 94% for LLM-based extraction (LlamaExtractor) on hard invoices**, with mathematical-validation error rates of 20% vs. 5% (arXiv:2510.15727, "Invoice Information Extraction") — so route hard tables to an LLM-extraction fallback.

4. **Small models are weak at open-domain SQL but strong at narrow-schema SQL.** On cross-domain BIRD, small models struggle; but your schema is fixed and narrow (result sheets, student records) — the regime where few-shot + schema-linking + self-correction pushes accuracy far higher. Self-correction is described in the on-prem BIRD frontier study (arXiv:2606.29733) as a "robust, near-free win" that is statistically significant across model families.

5. **Grammar-constrained decoding makes small-model SQL mechanically safer.** llama.cpp (which Ollama is built on) supports GBNF grammars that constrain output token-by-token to valid SQL, eliminating malformed-SQL parse failures entirely; grammar overhead in llama.cpp-based runtimes is "typically single-digit percent." Combined with a read-only DuckDB connection, row LIMITs, and query timeouts, this gives deterministic guardrails.

6. **Your hardware can be "superfast" for most queries via caching and warm-loading, but you must budget model swaps.** With only 4GB VRAM you cannot hold two 4B/7B models resident simultaneously; plan a single warm LLM plus swapping, or use one model for both extraction and SQL. Semantic caching reduces query latency 40–50% on repeated/rephrased queries.

## Details

### A. The core architecture: a four-way router over four engines

Your current system routes to three engines (vector/FACT, graph/LOCAL, community/GLOBAL). The fix is to add a **structured (SQL) engine** and upgrade the router to detect when a query needs computation vs. retrieval. As a Guild.ai routing overview notes, real deployments "need more than one data source… more than one vector store, graph DB, or even an SQL database," and query routing "decides which of those sources gets the query."

**Reference implementations to model on (all open-source/free):**
- **LlamaIndex `SQLRouterQueryEngine` / `NLSQLTableQueryEngine`** — the canonical open pattern for routing between a SQL database and a vector store; runs against Ollama local models (there is a working Open WebUI `text_to_sql_rag_pipe` built on `llama_index.llms.ollama`). This is the closest off-the-shelf match to what you need and integrates directly with your FastAPI backend.
- **LangChain SQL agents** — an agentic alternative with built-in self-correction loops.
- **Vanna.ai (MIT license)** — a purpose-built text-to-SQL RAG framework: you "train" a local vector store on your DDL + documentation + example question/SQL pairs, and at query time "Vanna will retrieve 10 most relevant pieces of training data and use it as part of the LLM prompt to generate the SQL." Works fully offline with Ollama + ChromaDB. This is the fastest path to a working SQL layer for a solo founder, and it has a self-reinforcing loop (good queries get saved as training examples). Note practitioners report the local-LLM version "is not as good as vanilla vanna with the API… query results are sometimes off," so pair it with guardrails and self-correction.

**Router design (rule-first, cheap, deterministic):** Do NOT use your slow 4B LLM as the first-line router. Use a fast rule-based + embedding classifier:
- **Rule layer (regex, microseconds):** scan for aggregation keywords — "how many", "count", "list all … who", "average", "total", "at least N", "more than", "percentage", "top", "rank". Presence → SQL route. This directly catches your failing query ("list of students who failed at least 4 subjects").
- **Embedding layer (semantic-router style, milliseconds):** pre-embed a handful of example utterances per route (FACT/LOCAL/GLOBAL/SQL) and route by nearest-centroid. The open-source `semantic-router` library (aurelio-labs) does exactly this — "instead of waiting for slow LLM generations… we use the magic of semantic vector space" — without an LLM call.
- **LLM fallback (only when ambiguous):** a single constrained call returning one route label.

This mirrors the production pattern in the clinical hybrid system Medi-Gemma (arXiv:2607.04907), which uses a strict rule-based priority hierarchy — a patient-ID regex routes to the clinical path; otherwise the engine "scans the prompt for data aggregation keywords, including how many, count, total, average, mean, percentage, breakdown, or census" and routes to statistical/SQL analytics.

### B. Getting messy documents into a queryable structured store

**The ingestion decision tree (per document):**
1. **Classify the document/region:** prose vs. table vs. scanned image. Docling already gives you layout info; use it as the router.
2. **Digital table, ruled/bordered:** Camelot lattice mode or Docling table mode. (Camelot "excels at lattice-based tables" and scored highest of the rule-based tools in the Tender category in the DocLayNet comparison, arXiv:2410.09871.)
3. **Digital table, borderless/whitespace-delimited:** pdfplumber — it "consistently delivered the best accuracy among open-source coordinate tools" on ambiguous column boundaries (Unstract 2026 comparison), though it needs per-format tuning and "becomes a liability as vendor count grows."
4. **Scanned/image PDF:** OCR first. **PaddleOCR (PP-Structure)** is the strongest open OCR for complex layouts and "natively handles table structure recognition… without additional libraries," reporting ~96% accuracy vs. Tesseract's ~75% on real-world docs; **Tesseract** is the CPU-only fallback for clean printed text (the "only option that works well without a GPU"). Preprocessing (deskew, binarize, upscale) yields "10-20 percentage points" of accuracy on hard scans.
5. **Irregular/inconsistent/semi-structured (the hard 20%):** **LLM-based extraction into a fixed schema.** Feed the raw text/table to the local LLM with a strict output schema (student_id, name, subject, marks, result, semester, department…) and use grammar-constrained/JSON-schema decoding so output is always valid. Tools: `Instructor` (structured extraction with Pydantic validation, works with Ollama), Simon Willison's `llm` + `sqlite-utils` (extracts structured records straight into SQLite/DuckDB via `llm logs --schema … | sqlite-utils insert`), or a custom validated loop (see DELM, arXiv:2509.20617, for a batched/validated/cached extraction pipeline pattern). This is slower (up to minutes/page) but robust to layout chaos — reserve it for documents the rule-based extractors fail on.

**Loading into DuckDB:** Normalize every extracted table to a canonical schema and append to DuckDB tables. Tag every row with `source_file`, `source_page`, `department`, `semester`, `ingest_timestamp` (mirroring your existing chunk metadata) so the SQL path can filter by department and every answer carries provenance.

**Critical schema-design insight:** text-to-SQL accuracy is markedly higher "when tables are consolidated into a single cohesive structure… LLMs perform better with single cohesive structures" (Promethium/LlamaIndex), with 80%+ reported on consolidated tables. So during ingestion, do the joining/normalization work up front (e.g., one wide `exam_results` table with one row per student-subject-semester) rather than forcing the 4B model to write multi-join SQL at query time. For "failed ≥4 subjects" this reduces to a trivial `SELECT student_id FROM exam_results WHERE result='FAIL' GROUP BY student_id HAVING COUNT(*)>=4`.

### C. Making a 4B model generate correct SQL

**The accuracy reality (sourced, protocol-dependent):**
- On **cross-domain BIRD** (hard, many schemas), raw zero-shot execution accuracy (EX): Qwen2.5-Coder-7B ≈ 45–51% (the on-prem frontier study, arXiv:2606.29733, reports 39.05% at 7B under a deliberately minimal greedy protocol; other papers report ~50.9%). Qwen2.5-3B-Instruct ≈ 30%; Qwen2.5-Coder-3B ≈ 31%. General vs. coder is roughly tied at 3B *zero-shot*; the coder pulls ~6–9 points ahead only after fine-tuning.
- On **Spider** (simpler, single-domain schemas — closer to your case), the same 7B coder is far stronger. With the SQL-R1 RL method (arXiv:2504.08600), **Qwen2.5-Coder-7B reached 87.6% on Spider dev, 88.7% on Spider test, and 63.1% on BIRD dev**, and even the **3B base reached 78.1% on Spider dev and 54.6% on BIRD dev.** The ~30-point Spider-over-BIRD gap is the single most important fact for you: **your narrow fixed schema is the easy regime.**
- With method (SFT + RL + self-consistency), the **SLM-SQL** paper (Cui et al., arXiv:2507.22478, GitHub CycloneBoy/slm_sql) drove tiny models remarkably far: **the 1.5B model achieved 70.49% EX on the BIRD test set and the 0.5B model 61.82%; on Spider, SLM-SQL-1.5B achieved 76.72% (dev) / 79.06% (test) and SLM-SQL-0.5B 72.08% / 73.5%** — surpassing several 7–15B baselines. A schema-enrichment + self-correction pipeline pushed Qwen2.5-Coder-14B to ~86% on Spider test on consumer hardware.
- A practitioner running qwen3-4b locally against a *simplified* semantic model reported ~90–95% accuracy at ~5–8s — but flagged run-to-run inconsistency as the real risk (informal blog; treat as indicative, not benchmarked).

**Coder vs. your current qwen3:4b-instruct:** The coder advantage is real but modest at small size and mostly appears after fine-tuning (~4–9 points; at 7B, Qwen2.5-Coder-7B beats general Qwen2.5-7B by ~4 BIRD / ~5 Spider points). For an MVP, your existing qwen3:4b-instruct with good prompting is a reasonable start; if SQL accuracy is your bottleneck, swapping the SQL path to **Qwen2.5-Coder-7B-Instruct (Q4)** or **defog SQLCoder-7B-2** (int4 ~3.1GB, fits 4GB) is the highest-leverage upgrade. Per Defog's founder, SQLCoder-7B-2 was "distilled from our 70B model, and performs roughly as well as GPT-4 for text-to-SQL generation" and is "much better at datetime and ratio queries than GPT-4" — though an independent breakdown notes join accuracy ~94% but WHERE-clause accuracy only ~77%, so guardrails and self-correction remain essential.

**The techniques that close the gap (stack all of them):**
1. **Schema-linking / schema-in-prompt:** put the full DDL of your (few, narrow) tables plus 2–3 sample rows and column descriptions in the prompt. On narrow schemas, providing the whole schema is cheap and effective; the frontier study found that on BIRD's already-narrow schemas "the prompt is rarely the bottleneck," so schema-link *pruning* matters mainly for wide schemas — for you, include the whole thing.
2. **Few-shot exemplars via retrieval (Vanna / DAIL-SQL / SPS-SQL pattern):** maintain a pool of question→SQL pairs; embed them; retrieve the k most similar to the incoming question and inject them. DAIL-SQL's dynamic few-shot selection reached 86.6% on Spider; SPS-SQL is designed specifically "to boost the Text-to-SQL accuracy on small-scale open-source LLMs." This is the single biggest lever for small models and requires no fine-tuning.
3. **Grammar-constrained decoding:** use llama.cpp GBNF (Ollama's `format`/structured outputs are built on it) so the model can only emit syntactically valid SQL — "malformed JSON [or SQL] becomes mechanically impossible."
4. **Execution-based self-correction loop:** run the SQL read-only against DuckDB; if it errors or returns an obviously empty/degenerate result, feed the error + query back to the model once or twice to repair. CogniSQL-R1-Zero (arXiv:2507.06013) shows execution feedback lifting Qwen2.5-7B-Coder from 52.0% to 60.0% single-sample EX on BIRD-dev; the frontier study confirms significance at p<10⁻¹⁰ across families.
5. **Self-consistency (optional, scale-stage):** sample 3–6 candidate queries and majority-vote on results (best-of-6 lifted CogniSQL to ~70%); adds accuracy but multiplies latency — skip on 4GB unless a query is high-value.
6. **Templated/constrained SQL for the top-N known question types:** for your most common analytical questions (backlogs per student, pass %, department toppers, attendance thresholds), pre-write parameterized SQL templates and have the LLM only fill slots (or match the query to a template via FAISS over template embeddings). This is the most reliable path and effectively guarantees correctness for the queries that matter most on Day 1.

**Guardrails (Day-1, non-negotiable):**
- **Read-only DuckDB connection** enforced at the driver level (reject INSERT/UPDATE/DELETE/DROP mechanically, not via prompt — "strictly more reliable than prompt-based guardrails alone," per the self-healing SQL engine study arXiv:2604.16511).
- **Hard row LIMIT** (e.g., 50–200) on returned rows.
- **Query timeout** to kill runaway scans.
- **Allowlist of tables/columns**; reject queries referencing anything else.

### D. Multi-department ingestion, isolation, and incremental updates (secondary, but design for it now)

- **Department scoping via metadata, enforced deterministically:** tag every chunk (vector), node (graph), and row (SQL) with `department`. Enforce isolation as a **hard filter in application code / SQL WHERE clause**, never by asking the LLM to "only use dept X" — LLM-layer filtering is a documented anti-pattern: "LLMs are probabilistic and susceptible to prompt injection… Enterprise security requires deterministic guarantees" (Truto). For a single-institution deployment where staff query across departments, use metadata filters (the "pool" model); if you later need hard walls (e.g., exam cell vs. general staff), move sensitive tables to separate DuckDB files/indices (the "silo" model). AWS's Bedrock pattern shows one knowledge base serving many departments via metadata filters "while providing logical document isolation."
- **Incremental ingestion:** LightRAG's Delta Index mechanism "builds local indexes only for newly inserted edges and entities… without the need for community reconstruction," letting you append new documents without full re-indexing — a major advantage over Microsoft GraphRAG, which "requires re-indexing of the whole knowledge graph… making it costly to integrate new information." For the SQL store, appending rows is trivial. Maintain an **idempotency ledger** (hash each file; skip already-processed files) so re-running ingestion is safe and cheap — a pattern used in production LLM ingestion pipelines (arXiv:2606.27384).
- **Provenance:** keep `source_file`/`source_page` on every row and chunk so every answer (semantic or aggregate) can cite its source — essential for institutional trust in "who failed" type answers.

### E. Serving on RTX 2050 4GB / 16GB RAM

- **Model residency:** You cannot fit two 4B/7B models in 4GB at once. Options: (a) one model (your qwen3:4b) for everything, (b) warm-load the primary model and accept a swap penalty when invoking a coder model for SQL, or (c) run the SQL coder model on CPU (slower but frees GPU). Keep the chosen LLM **warm-loaded** (Ollama `keep_alive`) so you never pay cold-start.
- **Quantization:** Q4_K_M is "the best value choice" for quality/size (your current choice is correct). INT4 vs INT8: at 4GB, Q4 is necessary; Q8 won't fit a 4B with usable context. A 4B model needs only ~2.5GB at Q4, leaving ~1.5GB for KV cache + overhead — which is exactly why your num_ctx=2048 cap is right.
- **KV cache & context:** your num_ctx=2048 cap is correct — bigger context spills to CPU/GPU split and causes the ~114s latency you observed. Enable **Flash Attention** (reduces VRAM "with zero quality degradation") and **KV-cache quantization** (`OLLAMA_KV_CACHE_TYPE=q8_0` or q4) to reclaim headroom and speed generation via reduced memory movement. Because narrow-schema SQL prompts are short (DDL + few-shot fits in ~1–2k tokens), the SQL path is not context-starved.
- **Keep FAISS + NetworkX graph in RAM** (16GB is ample for an institution's entity graph and vector index); pickle to disk for persistence, load once at startup.
- **Caching (biggest "superfast" lever):**
  - **Embedding cache:** never re-embed the same chunk/query text (persistent dict keyed by content hash).
  - **Semantic query cache (GPTCache, open-source):** embed incoming queries; on cosine similarity above threshold to a prior query, return the cached answer — "40-50 percent" latency reduction and ~30% GPU-memory savings on repeated queries. Set a conservative threshold (≥0.95) to avoid false hits.
  - **SQL result cache:** cache (normalized_SQL → result) so repeated aggregates are instant; invalidate on new ingestion into that table.
- **Realistic latency expectations:** cache hit → sub-second; SQL path (short prompt + fast DuckDB aggregate) → a few seconds dominated by LLM SQL generation; semantic RAG with generation at 2048 ctx → ~10–30s; anything that spills context to CPU → ~100s+ (avoid). The SQL path is actually your *fastest* route to a *correct* answer for aggregates, because DuckDB computes the aggregate in milliseconds and the LLM only writes a short query.
- **Is 4B enough, or go 7B/8B?** For semantic RAG and routing, 4B is fine. For SQL on a narrow schema with the full technique stack, 4B is workable but a 7B coder is meaningfully more reliable. The pragmatic answer: **keep 4B as the default, add a 7B coder only for the SQL path (CPU/offload), and lean on templated SQL + self-correction to compensate for model size rather than paying full 7B latency on every query.**

### F. Framework choice for the graph/RAG core

Your current NetworkX + FAISS + Louvain + LLM-summary stack is essentially a hand-rolled GraphRAG. Options worth knowing:
- **LightRAG** — dual-level retrieval, incremental delta indexing, far cheaper than Microsoft GraphRAG (reportedly <$0.01/document vs. $40–60), designed to run on local/HuggingFace models. Its incremental-update capability directly addresses your scale-stage "new documents arrive" need.
- **MiniRAG (HKU, ACL 2026, arXiv:2501.06713)** — purpose-built for small language models (targeting 1.5B–4B) on resource-constrained/edge hardware, using a "semantic-aware heterogeneous graph indexing mechanism that combines text chunks and named entities" plus lightweight topology retrieval; it "achieves comparable performance to LLM-based methods even when using SLMs while requiring only 25% of the storage space." If you ever rebuild the graph core, MiniRAG is the most on-point reference for a 4GB deployment.
- **nano-graphrag** — a minimal, readable GraphRAG implementation good for understanding/borrowing components (Naive/Local/Global modes mirror your FACT/LOCAL/GLOBAL).

You do **not** need Microsoft GraphRAG — it is expensive (many LLM calls per document), requires full re-indexing for updates, and is ill-suited to 4GB hardware.

## Recommendations

### MVP-now (Day 1 → ~4 weeks), in priority order
1. **Add the SQL engine and a fourth router route.** Stand up DuckDB. Define ONE consolidated `exam_results` table (plus a few canonical tables: students, attendance, faculty). Add a rule-based aggregation-keyword detector to your router that dispatches to the SQL path. This alone fixes your #1 blocker. *(Open-source, fits 4GB trivially, low complexity, Day-1.)*
2. **Wire text-to-SQL with the full small-model stack:** schema-in-prompt (DDL + sample rows) + retrieval-based few-shot exemplars (adopt **Vanna.ai** or **LlamaIndex NLSQLTableQueryEngine** to avoid building from scratch) + **read-only connection + row LIMIT + timeout** guardrails + **one-shot execution self-correction**. Start with qwen3:4b; if SQL accuracy < ~80% on a hand-labeled test set, swap the SQL path to Qwen2.5-Coder-7B (CPU/offload) or SQLCoder-7B-2. *(Open-source, medium complexity, Day-1.)*
3. **Pre-write parameterized SQL templates for your top 10–15 analytical questions** (backlogs ≥ N, pass %, toppers, attendance < X%, failures by subject/department). Match incoming queries to templates via FAISS over template embeddings; LLM only fills slots. This guarantees correctness for the queries that matter most. *(Open-source, low complexity, Day-1.)*
4. **Build the tiered table-extraction pipeline:** keep Docling for prose and easy tables; add pdfplumber (borderless) and Camelot (ruled) fallbacks; add an **LLM-extraction-into-schema fallback with JSON/GBNF-constrained output** for messy tables. Tag every row with department + provenance. *(Open-source, medium complexity, Day-1.)*
5. **Add caching:** embedding cache + GPTCache semantic query cache + SQL result cache. Enable Flash Attention + KV-cache quantization in Ollama; keep the model warm-loaded via `keep_alive`. *(Open-source, low complexity, Day-1 for the perf you want.)*
6. **Enforce department scoping as hard filters** in SQL WHERE clauses and vector metadata filters — never via prompt. *(Low complexity, Day-1.)*

### Scale-stage (as data and departments grow)
1. **OCR pipeline for scans:** add PaddleOCR (PP-Structure) with deskew/binarize preprocessing; Tesseract as CPU fallback. *(Open-source; PaddleOCR prefers GPU — run detection on CPU or during off-hours batch ingestion.)*
2. **Incremental ingestion at scale:** idempotency ledger (file-hash skip); adopt LightRAG-style delta indexing so new documents don't trigger full re-indexing.
3. **Isolation hardening:** move sensitive tables (exam cell, HR) to separate DuckDB files/indices if role-based walls become necessary.
4. **Consider MiniRAG** as the graph core if you rebuild — it's designed for exactly your SLM/4GB regime.
5. **Fine-tune the SQL model (LoRA)** on accumulated question→SQL pairs only if prompting plateaus below target; SLM-SQL shows SFT is the dominant lever for the smallest models (removing SFT dropped the 0.5B model by ~22 points), but it's operational overhead a solo founder should defer.
6. **Self-consistency voting** for high-value analytical queries where correctness > latency.

### Benchmarks/thresholds that should change your decisions
- **Build a labeled eval set of ~50–100 real institutional questions** (mix of semantic + aggregate) with gold answers. Measure execution accuracy on the SQL path — this is the only number that matters.
- **If narrow-schema SQL accuracy < 80%:** escalate model (7B coder) or expand few-shot pool / add templates before anything else.
- **If a query type keeps failing:** convert it to a hard-coded parameterized template.
- **If p95 latency on the SQL path > ~10s:** the bottleneck is LLM SQL generation — shorten prompts, cache more aggressively, or template the query.
- **If table-extraction row-accuracy < ~90% on a document type:** route that type to the LLM-extraction fallback.

## Caveats
- **Execution-accuracy numbers are protocol-dependent.** Reported small-model SQL scores vary widely by prompt template and eval harness (Qwen2.5-Coder-7B on BIRD ranges ~39–51% zero-shot; post-method numbers like SQL-R1's 63.1% BIRD / 88.7% Spider are *enhanced*, not zero-shot). Several strong small-model results (SLM-SQL test-set figures from the authors' GitHub; the qwen3-4b ~90–95% practitioner claim) are not peer-reviewed. Treat all figures as directional and validate on your own schema.
- **The "consolidate to one table" strategy trades ingestion complexity for query reliability.** You move the hard join/normalization work to ingestion time (where you control and validate it) instead of query time (where a 4B model fails at it). This is the right trade, but it concentrates your engineering effort in ingestion.
- **LLM-based table extraction can hallucinate values.** For grade sheets a wrong mark is worse than a missing row (the invoice study measured a 20% math-validation error rate for one method). Validate extracted numerics (range checks, row-count reconciliation vs. source, spot-audits) before trusting aggregates built on them.
- **Semantic caching on numeric/aggregate queries is risky** — "failed ≥4 subjects" and "failed ≥5 subjects" are semantically near-identical but need different answers. Use a high similarity threshold and prefer exact-match/normalized-SQL caching for the SQL path over semantic query caching.
- **4GB VRAM is a hard ceiling.** Every recommendation here respects it, but it fundamentally caps model quality and concurrency. If adoption grows, the single highest-ROI hardware upgrade is a GPU with 8–12GB VRAM (enough for a 7–8B model at Q4_K_M with usable context), which would eliminate most of the model-swap and latency compromises and let a stronger model handle both SQL and semantic paths resident simultaneously.
